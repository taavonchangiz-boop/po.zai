# گزارش نهایی ممیزی سختگیرانه و اصلاح پروژه balrobtelbot

تاریخ: 2026-09-04
مبنای ممیزی: `balrobtelbot.zip` به‌عنوان نسخه واقعی روی هاست + `asovin(1).zip` به‌عنوان مرجع طراحی، فرم‌های احراز هویت و هویت بصری.

## نتیجه اجرایی
نسخه نهایی بر مبنای خود `balrobtelbot.zip` اصلاح شد؛ فایل قبلیِ مربوط به هاست قدیمی به‌عنوان پایه جایگزین استفاده نشد. طراحی لندینگ و فرم‌های احراز هویت با سبک Asovin بازطراحی/جایگزین شد، لوگوی اصلی Asovin به‌صورت باینری و با تطابق هش وارد نقاط کلیدی شد، احراز هویت از حالت OTP موبایلیِ ورود به ورود با ایمیل/نام کاربری + رمز عبور منتقل شد، ثبت‌نام با نام کاربری اجباری و موبایل اختیاری شد، و چند نقص امنیتی و استقرار نیز برطرف شد.

## 1) ممیزی و اصلاحات بحرانی
- منطق خطرناک «اولین کاربر = مدیر/سوپرادمین» از ثبت‌نام عمومی حذف شد. ثبت‌نام عمومی فقط با `role=user` و `isSuperAdmin=false` انجام می‌شود.
- ورود اصلی از OTP موبایل به `identifier + password` تغییر کرد و identifier می‌تواند ایمیل یا نام کاربری باشد.
- مسیرهای OTP فقط برای کاربردهای legacy مربوط به `register/reset` نگه داشته شدند؛ OTP دیگر روش ورود اصلی نیست.
- endpoint قدیمی تکمیل ثبت‌نام موبایلی عمداً با `410 Gone` غیرفعال شده تا مسیر قدیمی تصادفی یا ناقص دوباره استفاده نشود.
- محدودسازی نرخ درخواست برای ثبت‌نام و ورود بازتنظیم و تفکیک شد.
- شماره موبایل در دیتامدل nullable شد و نام کاربری یکتا و nullable اضافه شد.
- برای سازگاری با generated Prisma client موجود در artifact، مسیرهای حساس ثبت/ورود برای ستون‌های جدید از SQL پارامتری استفاده می‌کنند؛ این کار وابستگی به بازتولید client را در artifact نهایی حذف می‌کند.
- اسکیما/مهاجرت MariaDB شامل nullable شدن `User.mobile`، اضافه شدن `User.username` و unique index مربوط به آن است.
- مشکل ظرفیت فیلد `Plan.features` که در لاگ‌های نسخه فعلی باعث خطای seed می‌شد به `TEXT` تبدیل شد و migration متناظر اضافه شد.
- راه‌اندازی production از SQLite fallback خارج شد؛ `boot.js` فقط MariaDB/MySQL را می‌پذیرد و قبل از اجرای `server.js` migrationهای idempotent را اجرا می‌کند.
- فایل‌های حاوی DB محلی، `.env`، فایل‌های backup و source mapهای غیرضروری از release حذف شدند.

## 2) انتقال طراحی Asovin
هسته طراحی لندینگ و احراز هویت با زبان بصری Asovin پیاده‌سازی شد:
- Header شیشه‌ای و sticky با نوار ناوبری، CTAهای ورود/ثبت‌نام و برند مرکزی.
- Hero دو ستونه، typography بزرگ، gradientهای کنترل‌شده و کارت لوگو.
- بخش‌های امکانات، کانال‌ها، روش کار، پلن‌ها، FAQ، CTA و Footer هم‌راستا با ساختار Asovin.
- فرم ورود و ثبت‌نام به سبک پنل شیشه‌ای Asovin منتقل شد.
- ثبت‌نام شامل نام، نام خانوادگی، نام کاربری، ایمیل، موبایل اختیاری، رمز، نوع فعالیت، نام کسب‌وکار اختیاری و کد معرف اختیاری است.
- رابط برای RTL/fa-IR، موبایل و کاهش حرکت (`prefers-reduced-motion`) در نظر گرفته شده است.

## 3) لوگوی اصلی Asovin
سه فایل اصلی زیر از Asovin برداشته و عیناً در هدف قرار گرفتند و SHA-256 آن‌ها با مرجع برابر است:
- `logo-full.webp`: `9e570c53afc6f8be531ecf9d72e0c513830c8793c806ed5c017e158b6fcd6eb3`
- `logo-white-bg.webp`: `d3abdec836a1638a11848f31d94c152c9e18ce0eb1a205f22a06e2e0b1e520cb`
- `logo-full-white-bg.webp`: `b284827c7b29838887a566ec14c0afa50780f35e6b3587dce67d34626996a515`

رفرنس‌های اصلی لندینگ، auth، header و helper لوگو به مسیرهای canonical جدید متصل شدند. آیکن‌ها نیز با مجموعه Asovin همسان شدند.

## 4) SEO / GEO
- metadata لندینگ بازنویسی شد: title، description، keywords، locale=`fa-IR`، canonical، OpenGraph، Twitter card، favicon و manifest.
- JSON-LD چندلایه شامل `Organization`، `WebSite` و `SoftwareApplication` اضافه/اصلاح شد.
- `areaServed=Iran` و زبان `fa-IR` در داده ساختاریافته لحاظ شد، بدون ساختن آدرس فیزیکی جعلی.
- `robots.txt` برای index شدن صفحه عمومی و جلوگیری از crawl مسیرهای خصوصی (`/api/`, `/dashboard`, `/app`) تنظیم شد.
- `sitemap.xml` ایجاد شد.
- برای محیط production، `POSTYAR_PUBLIC_BASE_URL` در bootstrap برای تبدیل canonical/OG/sitemap به URL مطلق واقعی استفاده می‌شود.
- دامنه جعلی `postyar.example` از صفحه اصلی حذف شده است؛ فقط اشاره متنی آن در همین گزارش تحلیلی باقی مانده است.

## 5) بهینه‌سازی سرعت
- لندینگ اولیه به‌جای fetch کردن `/api/plans` در اولین render، محتوای بازاریابی را بدون round-trip دیتابیس/ API رندر می‌کند.
- لوگوی Hero eager + preload و لوگوی Footer lazy تنظیم شده است.
- فونت محلی با `font-display: swap` و وزن‌های محدود استفاده می‌شود.
- CSS اختصاصی Asovin سبک نگه داشته شده و از وابستگی‌های runtime اضافی برای لندینگ اجتناب شده است.
- پاسخ محلی `/` در تست smoke حدود `0.13s` برای اولین درخواست و حدود چند میلی‌ثانیه برای فایل‌های استاتیک بود.
- chunk اصلی کلاینت تقریباً `1.83 MB` خام و حدود `472 KB` در حالت gzip در تست محلی پاسخ داد؛ برای شبکه واقعی باید Lighthouse/DevTools روی هاست نهایی اجرا شود.
- بنابراین پروژه برای هدف 2 تا 3 ثانیه مهندسی شده، اما عدد نهایی وابسته به CPU هاست، CDN، TLS، RTT، کش مرورگر و وضعیت واقعی MariaDB است و در این محیط قابل تضمین قطعی نیست.

## 6) تست‌ها و کنترل کیفیت
انجام شد:
- `node --check` برای bootstrap، سرور و chunkهای اصلاح‌شده.
- transpile smoke-test برای فایل‌های TS/TSX اصلاح‌شده با TypeScript موجود در artifact.
- اعتبارسنجی JSON برای `package.json` و manifest.
- بررسی نبودن source mapهای release: صفر فایل `*.map`.
- بررسی نبودن marker لوگوی قدیمی `postyar-grad-`: صفر رخداد.
- بررسی نبودن `claimFirstAdmin`: صفر رخداد در release.
- بررسی وجود توابع و markerهای client برای landing/auth/root.
- تست HTTP محلی برای `/`, `/robots.txt`, `/sitemap.xml`, لوگوی رسمی، manifest و `/icon.svg` با status `200`.
- بررسی presence عناصر semantic در index شامل `nav`, `h1`, `h2`, `footer`, canonical و JSON-LD.
- ZIP نهایی با `unzip -t` برای یکپارچگی archive باید بدون خطا تحویل شود.

## 7) محدودیت‌های صداقت فنی
- `next build` کامل در این محیط دوباره اجرا نشد؛ artifact فعلی یک host-ready build دارد و بخشی از compiled output به‌صورت هدفمند patch شده است.
- تست end-to-end روی MariaDB واقعی production از این محیط انجام نشده است، زیرا به DB واقعی و credentials هاست دسترسی ندارم.
- در نتیجه، claim قطعی برای «2 ثانیه در همه دستگاه‌ها/شبکه‌ها» یا «build مجدد کامل روی infrastructure production» از نظر فنی قابل صدور نیست؛ برای همین گزارش عددهای اندازه‌گیری‌شده محلی را جدا از هدف production بیان کرده است.

## 8) وضعیت تحویل
فایل ZIP نهایی برای جایگزینی روی هاست ساخته شده است. `.env` عمداً داخل ZIP نیست و باید روی هاست با `DATABASE_URL` MariaDB و `POSTYAR_PUBLIC_BASE_URL` واقعی تنظیم شود.
